> 生成日期：2026-08-01
> 适用对象：DDW AI Hub 底座平台 + 所有插件项目

## 十五条 DDW OPC 经营准则

### 准则 1：密度优先 —— 衡量"单位投入产出比"，不是"总规模"

**面壁经验**：Densing Law——每 100 天模型能力密度翻一番。MiniCPM-2B 打平 Mistral-7B。

**DDW 应用**：
- 每个插件开发前必须问："能不能用更小模型？能不能砍掉一个依赖？能不能少一个云服务？"
- 插件资源消耗声明（Phase 5.4）就是密度思维的落地——把 CPU/内存/Token 消耗量化
- 选 LLM 时优先本地小模型（Qwen3-8B/GLM-4-9B），云端仅用于复杂推理

**落地检查**：每次插件发布前，资源消耗声明必须填写完整，不可跳过。

---

### 准则 2：细分护城河 —— 用 22 年制造业 know-how + CFA ESG 做交叉壁垒

**面壁经验**：不跟 DeepSeek 卷云端旗舰，只在"端侧+国产芯片"做第一。

**DDW 应用**：
- 你的护城河 = **制造业 22 年实操经验 × CFA ESG 认证 × 湖北产业资源**
- 不要做"另一个 Coze"、"另一个 Dify"——正面竞争必死
- DDW 的定位：**制造企业 AI 落地的底座平台**（不是通用 Agent 平台）
- ESG 插件套件：**光通讯模块出口 ESG 合规**——这是别人抢不走的细分
- 智能客服：**制造业设备维护工单 Agent**——不是通用客服

**落地检查**：每个新插件立项时，必须回答"这个插件的 know-how 壁垒是什么？别人抄不走的是什么？"

---

### 准则 3：先跑通，再包装 —— 产品能用了再写文章

**面壁经验**：ChatDev 上线不到一周 1.2 万 Star。每次开源配套 Cookbook + 部署包 + 论文。

**DDW 应用**：
- 每个插件发布时必须配套 **"5 分钟跑通"教程**（Docker 一键启动 + 演示 Demo）
- 插件在 GitHub 上 README 第一屏就是 Quick Start（参考 MiniCPM 5-step 部署）
- 等产品稳定了再写公众号/知乎/掘金文章——不要先吹再补
- 技术博客节奏：**每 2 周 1 篇**，持续露出建立影响力

**落地检查**：每个插件 README.md 第一屏必须有 `## Quick Start` 段落，5 步内可跑通。

---

### 准则 4：渐进式开源 → 商业化 —— Apache 2.0 打底，不搞"先免费后收费"

**面壁经验**：MiniCPM 先学术免费 → 社区认可 → 硬件厂找上门 → 商业化。但早期"学术免费+商业需联系"策略有问题。

**DDW 应用**：
- ✅ 已明确 Apache 2.0——正确策略，保持
- 开源引流路径：GitHub → 技术人员试用 → 成为 DDW 平台研究者 → 企业采购
- 不要在协议上搞"社区版/企业版"双版本——直接用 Apache 2.0 + 商业支持服务
- 私有商业插件（ESG 套件）走独立授权，不混入开源仓库

**落地检查**：所有公开仓库 LICENSE 文件统一 Apache 2.0，GitHub 简介标注清楚。

---

### 准则 5：聚焦 1-2 条主线 —— 80% 精力在能变现的项目上

**面壁经验**：面壁 9 条线并行但只有 MiniCPM 赚钱。OPC 最容易踩的坑就是"项目多、都不深入"。

**DDW 应用（最重要的一条）**：
- **只能有 1-2 个主项目**，其他砍掉或冻结
- 建议主项目分类：

| 优先级 | 项目 | 理由 |
|:------:|:-----|:-----|
| 🥇 主线 | **DDW AI Hub 底座平台**（含 Token Manager + LLM Gateway） | 所有项目的底座，不可砍 |
| 🥇 主线 | **ESG 插件套件**（6 插件） | 有 know-how 壁垒 + 可直接变现（光通讯模块 ESG 合规） |
| 🥈 衍生 | **Smart CS 智能客服** | 制造业设备维护工单 Agent → 可快速变现 |
| 🔒 冻结 | hotwuhan / ruiguo / oral-clinic / operations / knowledge-base / feishu-multi-agent | 已有用户在用则维持，但**不再新增功能** |
| ❌ 暂缓 | Email Assistant / DC3 Connector | 等主线跑通后再激活 |

**落地检查**：每月复盘一次项目清单，问自己"这个月主线项目投入时间是否 ≥80%？"

---

### 准则 6：早期就找付费种子用户 —— 不追 Star 数据

**面壁经验**：StaffDeck 1.3k Star 仍无付费客户。

**DDW 应用**：
- GitHub Star 是手段不是目的——真正衡量标准是 **"有几个付费客户"**
- ESG 插件套件：找你熟悉的制造业老板，免费试用 1 个月后谈付费
- Smart CS：找你熟悉的工厂，先装一套跑起来，收集反馈再定价
- 定价参考：Dify 云版 ¥99/月起、企业私有化部署 ¥5,000-50,000/年

**落地检查**：3 个月内至少找到 **1 个付费种子客户**（哪怕只收 ¥99/月）。

---

### 准则 7：保持 API/接口稳定 —— 不搞大重构

**面壁经验**：ChatDev 1.0 → 2.0 大重构让社区迷茫。

**DDW 应用**：
- 插件 SDK（plugin_base.py）的公开接口一旦发布，**只增不改**
- API 路径格式 `/api/v1/plugins/{plugin-name}/` 永久不变
- 如果确实要大改，新版本作为独立插件发布（如 `ddw-esg-v2`），旧版本维持 6 个月过渡期
- 每次 manifest.yaml 版本号变化必须在 CHANGELOG.md 中写清楚 breaking changes

**落地检查**：任何 SDK 接口修改必须先检查"现有插件会不会被破坏"，pytest 全部通过才能合并。

---

### 准则 8：可移植性 —— 支持多种 LLM + 多种部署方式

**面壁经验**：ForgeTrain 强烈绑定 Cursor，agent-agnostic 失败。

**DDW 应用**：
- ✅ DDW LLM Gateway 已解决多 Provider 问题——正确
- 插件不直接配置 LLM Provider，全部走 DDW 网关
- 支持部署方式：Docker Compose（本地）+ ECS（云端）+ 纯本地 Ollama（离线）
- 不绑定任何单一 LLM 厂商——用户自己选 Provider

**落地检查**：任何插件不得在自己的代码中 hardcode LLM Provider 或 API Key。

---

### 准则 9：用 Apache 2.0，不用 AGPL

**面壁经验**：StaffDeck 用 AGPL-3.0 传染性协议，给企业客户造成法务障碍。

**DDW 应用**：
- ✅ DDW 已选 Apache 2.0——正确，坚持
- 引用 MIT/Apache 2.0 代码时创建 NOTICE 文件（已有流程）
- 绝对不用 GPL/AGPL 协议的代码到 DDW 源码中（只用连接器模式对接 AGPL 项目）
- ESG 私有插件：独立授权协议，不混入开源仓库

**落地检查**：每次 git push 前检查 LICENSE 文件一致性。引用外部代码时必须更新 NOTICE。

---

### 准则 10：准备 Plan B —— 不押注单一合作

**面壁经验**：ChatDev SaaS 过度依赖 modelbest.cn。

**DDW 应用**：
- 每个插件的核心功能要能脱离任何第三方服务独立运行
- 云端 LLM 挂了 → 降级到本地 Ollama
- ECS 挂了 → Docker Compose 本地也能跑
- 飞书/企微渠道被封 → Web UI 仍然可用
- 不签独家合作（至少前 2 年）

**落地检查**：每个插件至少支持 2 种部署方式，至少对接 2 种 LLM Provider。

---

### 准则 11：MVP 最小可用版本 —— 2 周出原型，不追求完美

**面壁经验**：MiniCPM 1.0 就是 2.4B 参数、2 周训练出来的。

**DDW 应用**：
- 新插件开发周期：**调研 1 周 → MVP 开发 1 周 → 测试 3 天 → 上线**
- MVP 标准：**核心功能能跑 + 有 1 个 Demo + README 能跑通**
- 不要在第一版就做权限引擎、Dashboard、多租户——这些是有了付费客户后的事
- "先做出能用的，再迭代"——不是"先设计完美的，再动手"

**落地检查**：新插件从立项到 MVP 上线不超过 3 周。超过就说明范围太大了，砍需求。

---

### 准则 12：场景为王 —— 垂直一个场景做透，不做通用平台

**面壁经验**：靠"端侧"避开云端红海。

**DDW 应用**：
- 不要做"通用 Agent 平台"——和 Coze/Dify 正面竞争必死
- 聚焦 **"制造业设备维护工单 Agent"**——一个场景做透
- 聚焦 **"光通讯模块出口 ESG 合规"**——一个场景做透
- 赢了这两个场景再考虑扩展

**落地检查**：每个插件的定位描述必须是"XX 行业的 XX 场景"，不能是"通用 XX 平台"。

---

### 准则 13：学会说"不" —— 砍需求、砍客户、砍功能

**面壁经验**：至少砍掉了多个早期方向。

**DDW 应用**：
- 当用户/客户提需求时，先问"这个需求是不是 80% 用户都需要的？"
- 低于 20% 用户需要的功能 → 不做
- 不付钱的客户提大需求 → 先签合同再开发
- 免费用户只享受标准功能，定制化需求单独报价
- 每个月审视一次插件功能清单，砍掉使用率 <5% 的功能

**落地检查**：每次插件迭代时，至少砍掉 1 个低价值功能或关闭 1 个低活跃项目。

---

### 准则 14：杠杆用足 —— 你的杠杆 = 制造业 know-how + CFA ESG + 湖北资源

**面壁经验**：用清华学术影响力拿融资、用 GitHub 拿开发者、用国产芯片政策拿大客户。

**DDW 应用**：
- **制造业 know-how**：写"制造业 + AI"系列技术博客，建立行业专家形象
- **CFA ESG**：写"ESG 合规 + AI"系列，在 ESG 圈建立技术流品牌
- **湖北资源**：武汉光谷 → 光通讯产业集群 → 你的第一批客户就在家门口
- **GitHub**：开源 = 最低成本的获客渠道（已有 6 个公开仓库）
- **知乎/掘金/公众号**：每 2 周 1 篇技术文章，持续露出

**落地检查**：每周至少用 1 个杠杆（发文章/更新 GitHub/联系湖北企业）。

---

### 准则 15：节奏控制 —— 3 阶段推进，不跳级

**面壁经验**：4 个月迭代一个 MiniCPM 版本，不急不躁。

**DDW 应用（三阶段路线图）**：

| 阶段 | 时间 | 目标 | DDW 当前进度 |
|:----:|:-----|:-----|:------------|
| **第 1 阶段** | 0-3 个月 | 做出"能跑的最小版本" | ✅ 已完成（底座 + 多插件已上线） |
| **第 2 阶段** | 3-6 个月 | 做出"生产可用的" + 找付费种子用户 | 🔄 进行中 |
| **第 3 阶段** | 6-12 个月 | 验证 SaaS + 私有化双轨商业模式 | ⏳ 待启动 |

**第 2 阶段具体任务**：
1. 接入 MCP 协议（已完成）
2. 接入飞书/企微（已部分完成）
3. Trace + 用户反馈 + 人工兜底
4. **找到 1-2 个付费种子客户**（当前优先级最高）
5. 知乎/掘金/公众号技术博客（每 2 周 1 篇）

**落地检查**：每季度末对照三阶段表检查进度，不跳级。
