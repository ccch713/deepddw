🛡️ 问题 1：7 天免费试用 · 防服务器时间篡改 + 自动生成 POC 报告
业务需求
  • 市场所有付费插件支持 7 天免费试用
  • 插件在试用期内全功能可用
  • 试用到期自动停止，提示购买
  • 无需任何人工审批，IT 人员自助操作
POC 测试报告 PDF
  • 试用期间自动记录 POC 验证数据
  • 支持企业 IT 一键导出可下载 PDF
  • PDF 成为内部预算审批、立项的正式文件
  • 含：验证日期、插件版本、测试结论、环境信息
攻击场景
  • IT 人员改服务器系统时间（date 命令）
  • 容器内改 TZ 环境变量 + 系统时间
  • 修改 Docker 容器的时间偏移
  • 试用到期后重装系统重新计时
  • 删除许可证文件重新申请试用
🔒 核心原则——不信任本地时钟，信任密码学签名
一人公司不需要反破解团队对抗全世界的黑客。你只需要做到：让"绕过试用"的代价比"直接买"更高。
以下是三层防线，递进保护。第一层挡住 80% 的顺手改时间，第二层挡住认真尝试，第三层让违规者无法拿到 POC 报告（等于拿不到预算审批文件）。

# 时间胶囊结构（JWT 格式，RSA 签名） { "plugin_id": "medical_records@1.2.0", "device_fingerprint": "a1b2c3d4e5f6...", "trial_start": "2026-06-27T10:00:00Z", # ← 市场 API 时钟 "trial_end": "2026-07-04T10:00:00Z", # ← 市场 API 时钟 "signature": "RSA-SHA256(...)" # ← 你的私钥签名 }
第二层：每次加载校验 → 本地签名验证
攻击 1：改服务器时间
平台不信任本地时间。
每次插件加载时校验：
RSA.verify(时间胶囊)
取当前时间 → 只和 trial_end 比较。
如果时间被改到过去：平台从市场 API 获取"最新服务器时间戳"做二次校验 → 检测到时间跳变 → 立即标记为"异常试用" → 停止插件运行 + 通知插件作者。
如果时间被改到未来：trial_end 被超过 → 试用到期，停用。
攻击 2：重装系统/删文件
设备指纹包含：
sha256(mac + disk_serial + hostname + uuid)

重装系统后 MAC 地址不变、磁盘序列号不变 → 设备指纹相同 → 再次向市场 API 申请试用 → API 发现该设备已试用过 → 拒绝。

虚拟机克隆攻击：克隆后的 MAC 地址可能相同 → 同样被设备指纹锁定。
攻击 3：改源码绕过
这是最难防的。开源源码改掉校验逻辑？

反制：插件本身也是打包的 .ddwplugin，校验逻辑在 Plugin SDK 里。如果用户改了平台源码跳过了许可证检查，但插件的代码在加载时会调用 market API 校验自己的许可证。

插件作者可以在插件代码里加一层校验：
LicenseValidator.assert_valid(plugin_id)
这层校验在插件进程内跑，不在平台代码里。
第三层（杀手锏）：POC 测试报告就是最好的"禁止违规"机制

为什么这对一人公司有效：
  • IT 人员改时间绕过了试用 → 但拿不到干净的 POC 报告
  • 没有干净 POC 报告 → 无法走内部预算审批流程
  • 无法走预算审批 → 买不了正版 → 项目无法推进
  • 违规的 IT 人员自己也没办法向老板交差
  • POC 报告的在线核验链接：财务/法务一扫就知真假
✅ 问题 1 结论：防破解就靠 3 样东西——不用你派人对抗
① 时间胶囊 RSA 签名（不信任本地时钟，市场 API 给你签名时间）
② 设备指纹（屏蔽重装、克隆、重新试用）
③ POC 报告在线核验（违规者拿不到预算审批所需的干净报告）

三条全部靠 Python 标准库（cryptography/hashlib/uuid）实现，不需要反作弊团队。一人公司完全撑得住。
🔗 问题 2：开发者间联调授权 · "向原插件作者申请"机制
业务场景
  • 开发者 B 开发新插件需要集成付费插件 A
  • 开发者 B 不应为"联调开发"购买完整企业授权
  • 需要一个"开发者联调许可证"机制
  • 原插件作者控制：给谁、给多久、能否续期
流程设计
  • 开发者 B 在市场找到插件 A → 点击"申请联调授权"
  • 平台向插件作者 A 发送私信通知（平台内消息）
  • 插件作者 A 在管理后台看到申请详情（B 的开发者档案、计划开发的插件）
  • A 决定授权 → 选择授权期限（14 天 / 30 天 / 自定义）
  • B 的设备收到联调许可证 → 插件 A 在 B 的开发环境中激活
续期与终止
  • 授权到期前 3 天 → 平台自动发送续期提醒给双方
  • 插件作者 A 可选择：同意续期 / 不同意 / 要求升级为付费
  • 授权到期后 → 插件 A 在 B 的环境自动停用
  • 如果 B 的插件已上架市场 → 可申请"相互授权"（互免）
⚖️ 为什么这个机制不会被滥用？
① 每个开发者都有实名信誉体系（插件发布记录、评价、下载量）→ 乱申请的会被其他开发者拉黑
② 联调许可证绑定设备指纹 + 社区版用户限制（≤3 人）→ 不能用于生产环境
③ 插件作者完全控制授权——不想给可以拒绝，没有强制义务
④ 联调许可证的插件内会显示"⚡ DEV 联调模式"水印，提醒这不是正式授权
⑤ 在平台私信里交流，所有对话留痕，防止纠纷

✅ 问题 2 结论：授权流程 + 技术执行都简单
技术层面：复用"时间胶囊"签名机制。Plugin Author 的"授权" = 用 market API 私钥签发一个"联调许可证"，和试用许可证是同一套基础设施。

业务层面：插件作者完全掌控授权。平台只做通知 + 签名执行。"开发者互信"拉动生态——我让你联调，你上架后也可能让我联调。

开发者不可绕过：联调许可证也绑定设备指纹 + 时间签名。不能复制给别人用、不能无限续期。

对一人公司的意义：这个机制零人工成本——平台自动发通知、自动生成授权、自动停用。你不需要参与任何一次授权决策，全交给插件作者们自己玩。
