## 一、现状实测

### 1.1 建表机制

```python
# core/database/session.py:74
async def init_db() -> None:
    """启动时建表（仅 dev 用，生产用 Alembic）。"""
    engine = get_engine()
    async with engine.begin() as conn:
        from core.database import models  # noqa: F401  触发模型注册
        await conn.run_sync(Base.metadata.create_all)
```

- **注释声称"生产用 Alembic"，实际代码中没有 Alembic**（requirements.txt 无、pip 未装）——注释与实现不符
- 生产 ECS 实测：主库 89 张表 = 平台 Base 7 个模型 + 插件注册模型（43 个插件文件含 create_all）
- 插件独立建表：`plugins/*/plugin.py` 内各自 `Base.metadata.create_all`（43 处），如 kh 插件对主库/向量库分别建表

### 1.2 迁移能力现状

| 场景 | 现状能力 | 风险 |
|------|---------|------|
| 新增表 | ✅ create_all 自动建 | 无 |
| 新增列（nullable） | ❌ 不自动 | 需手工 DDL 或删库 |
| 改列类型/约束 | ❌ 不自动 | 数据丢失风险 |
| 删表/重命名 | ❌ 不自动 | 需手工 |
| 多 worker 并发建表 | ⚠️ SQLite 单写者，create_all 幂等 | 低（单 worker 部署） |

## 二、引入 Alembic 的评估

### 2.1 可选方案

| 方案 | 说明 | 优点 | 缺点 | 适配度 |
|------|------|------|------|--------|
| **A. 不引入，保持 create_all** | 维持现状 + 修正误导注释 | 零改动、启动即建表、插件自治 | schema 演进全靠手工 | 当前单机 SQLite 部署足够 |
| **B. 全量引入 Alembic** | 主库 + 每个插件库都纳入 alembic | 标准迁移、可回滚 | 43 个插件都要建 migration，维护成本爆炸；插件自治模式与集中迁移冲突 | ❌ 过度设计 |
| **C. 轻量 schema_version 表** | 主库建 `schema_versions` 表，平台核心模型用增量脚本，插件仍自治 | 核心 schema 可演进、成本低、不动插件 | 非标准方案，需自研 | ✅ 推荐 |
| **D. 仅修正注释** | init_db 注释改为"生产主库用 create_all，schema 演进见 docs" | 诚实文档 | 无实际迁移能力 | 最低成本 |

### 2.2 决策建议：方案 C（轻量）+ 方案 D（注释修正）组合

**理由**：
1. 当前部署形态 = 单机 SQLite + 单 worker，表结构变更频率低（3 个月 1-2 次）
2. 43 个插件各自自治建表，与 Alembic 集中迁移哲学冲突——强行引入会让每个插件都要维护 migration 链
3. 真正的迁移需求集中在**平台核心表**（users/tenants/token_quotas 等 7 个），这 7 个表用轻量版本表管理即可
4. 若未来 PostgreSQL + 多 worker SaaS 化，再升级为完整 Alembic（届时插件市场是独立生命周期，插件库迁移由插件作者负责）

### 2.3 方案 C 落地设计（P3 长期，不排今晚）

```python
# core/database/schema_version.py（设计稿）
# 主库建表：
#   schema_versions (version INTEGER PRIMARY KEY, applied_at TEXT)
# 迁移脚本目录：core/database/migrations/0001_xxx.py, 0002_xxx.py ...
# 启动顺序：init_db() 后 → get_current_version() → 顺序执行未应用迁移 → 记录版本
# 迁移脚本约定：upgrade(conn) / downgrade(conn) 双函数，事务包裹
```

## 三、结论

| 项 | 结论 |
|----|------|
| 是否需要 Alembic | **当前不需要**（单机 SQLite 单 worker 形态） |
| 立即动作 | 修正 init_db 误导注释（方案 D）—— 今日执行 |
| 长期方案 | 方案 C 轻量 schema_versions（PostgreSQL SaaS 化时升级完整 Alembic） |
| 触发升级条件 | ① 部署形态变 PostgreSQL ② 多 worker ③ 表结构月变更 ≥2 次 |
