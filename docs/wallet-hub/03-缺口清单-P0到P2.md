## 🔴 P0 — 阻塞问渠接入（必须解决）

### P0-1：三钱包拆账（skin / income / recharge）

**问题**：`WalletAccount` 只有 `balance_cents` 单字段。问渠需要：
- `recharge_balance_cents`（实收→消费）—— 微信充值入账
- `income_balance_cents`（可提现→消费兜底）—— 皮肤分成 / 资料贡献
- `skin_balance`（虚拟币，不可提现）—— 平台发放的可消费余额

**当前模型**：
```python
class WalletAccount(WalletBase):
    __tablename__ = "dw_wallet_accounts"
    user_id: Mapped[str] = mapped_column(String(64), unique=True)
    balance_cents: Mapped[int] = mapped_column(Integer, default=0)
    frozen_cents: Mapped[int] = mapped_column(Integer, default=0)
    # ... 没有拆账维度
```

**改造方案 A（推荐）**：增加字段而非拆表
```python
class WalletAccount(WalletBase):
    user_id: Mapped[str] = mapped_column(String(64), unique=True)
    recharge_balance_cents: Mapped[int] = mapped_column(Integer, default=0)
    income_balance_cents: Mapped[int] = mapped_column(Integer, default=0)
    skin_balance: Mapped[int] = mapped_column(Integer, default=0)
    frozen_cents: Mapped[int] = mapped_column(Integer, default=0)
```

**代价**：
- `credit_balance` / `debit_balance` 需要 `target: Literal["recharge", "income", "skin"]` 参数
- 流水表 `ChargeRecord` 增加 `balance_type` 字段
- 不破坏现有余额语义（已有用户的 `balance_cents` → `recharge_balance_cents` 一次性迁移）

**工作量**：3-5 天（含迁移脚本）

---

### P0-2：混合扣费优先级

**问题**：`debit_balance()` 只扣单字段。问渠需要：

```
扣费发起（按量计费）
    ↓
1. 先扣 recharge_balance_cents
    ↓ (余额不足)
2. 兜底扣 income_balance_cents
    ↓ (两个都不足)
3. 兜底扣 skin_balance (如果允许)
    ↓ (都扣完仍不足)
4. 返 402 InsufficientBalanceError
```

**改造方案**：新增 `charge_with_fallback(session, user_id, amount, fallback_chain)`
- 单事务内逐钱包扣减，乐观锁防并发
- 记录每段扣减的 `balance_type` 到 `ChargeRecord`（新增字段）
- 任一段失败则整体回滚

**代价**：`charge.py` 重构（约 100 行），需新增测试覆盖 3 段扣减组合。

**工作量**：2-3 天

### P0-3：自动对账引擎

**问题**：当前无对账引擎。问渠需求：
- 每日 03:00 自动拉微信**前一天**账单（API v3 `/v3/bill/fundflowbill`）
- 比对 `RechargeOrder`（本地）vs 微信账单
- 三方对账：微信账单 ↔ 本地 PayTransaction ↔ Ledger（账户流水）
- 差异生成对账报告 → 财务确认 → 自动调补救接口

**当前缺失**：
- 无 `wechat_bill_fetcher`（账单拉取）
- 无 `reconciliation_engine`（对账引擎）
- 无 cron 调度（依赖 systemd 或 celery）
- 无差异告警机制

**改造方案**：
```python
# 新增 services/reconciliation.py
async def daily_reconciliation(target_date: date) -> ReconciliationReport:
    bill = await fetch_wechat_bill(target_date)
    local_orders = await get_local_recharge_orders(target_date)
    diff = compare(bill, local_orders)
    if diff: notify_finance(diff)
    return ReconciliationReport(...)
```

**代价**：需新增 ~300 行 + 微信账单 API 适配 + 差异规则引擎。

**工作量**：5-7 天

### P0-4：退款链路未接通

**问题**：`refund_balance()` 仅写本地记录，**未调微信退款 API**。

```python
# 当前 refund.py L76-77
# 真实环境：异步调用微信/支付宝退款接口
# _call_provider_refund(order.order_no, refund_no, ...)
```

**改造方案**：新增 `services/wechat_pay.py::create_refund()`（已有 `wechatpayv3.refund()` 集成）+ `refund_balance()` 内调用：
```python
async def refund_balance(session, user_id, amount_cents, reason):
    # 1. 找原充值单
    # 2. 扣余额
    # 3. 创建本地 refund 记录
    # 4. 调微信 refund API → 设置 status='processing' 或 'success'
    # 5. 微信异步通知回调 → 更新 status='success'
```

**代价**：
- 新增 `wechat_refund_callback` 端点（schema 已有）
- `refund.py` 接入真实 SDK 调用
- 测试微信退款场景（部分退款/全额退款）

**工作量**：2 天

---

### P0-5：平台抽佣逻辑

**问题**：当前 `royalty.py` 只有"课件分成给作者"（80%/50%），**没有"平台抽 X%"**。

问渠需求：
```
一笔交易 ¥100
    ↓
扣费 ¥100
    ↓
平台抽佣 5%（¥5）→ 平台账户（新增 PlatformAccount）
    ↓
课件作者分成 ¥80 (若作者归属此交易)
    ↓
剩余 ¥15 → 实际消费结转（无作者时归平台）
```

**改造方案**：
- `royalty.py::settle_royalty` 增加 `platform_fee_percent` 参数
- 新增 `dw_wallet_platform_accounts` 表（平台分账账户）
- 扣费时自动触发：先入平台，再分作者

**代价**：模型新增表 + 服务层逻辑扩展 + 财务报表接口。

**工作量**：3-4 天

## 🟡 P1 — 运营风险（不阻塞但需在规模化前解决）

### P1-1：多租户缺失

**问题**：`WalletBase` 独立 DeclarativeBase，**所有表都无 `tenant_id`**。问渠需求：
- 多家教育机构（华师一附中 / 洪山高中 / 其他加盟校）共用一套系统
- 每家独立结算、独立查看自家学生的余额
- 防止跨校误操作

**改造方案**：所有 6 张表加 `tenant_id: String(32) NOT NULL` + 复合索引 `(tenant_id, user_id)`。`get_or_create_account` / `charge` / `refund` 强制传入 `tenant_id`。

**工作量**：2-3 天（每张表加字段 + 所有服务层函数加参数 + 路由层取 tenant 上下文）

---

### P1-2：余额冻结未实现

**问题**：`frozen_cents` 字段预留但代码无任何读写。

**应用场景**：
- 秒杀下单：先冻结 1 分钟，超时释放
- 退款中：冻结对应金额，避免重复扣
- 风控：临时冻结可疑账户

**改造方案**：实现 `freeze_balance(session, user_id, amount)` / `unfreeze_balance()`，复用乐观锁。

**工作量**：1-2 天

---

### P1-3：流水无租户过滤

**问题**：`list_transactions(user_id)` 只按 user_id 查，多租户场景下能跨租户查别人的流水（user_id 是 String 不唯一跨租户）。

**改造方案**：强制 `list_transactions(user_id, tenant_id)` 复合查询 + 索引。

**工作量**：0.5 天

---

### P1-4：对账无引擎（已在 P0-3 中包含部分）

**问题**：见 P0-3。

**额外需求**：
- 手工对账触发（管理后台"立即对账"按钮）
- 对账历史记录（`dw_wallet_reconciliation_logs` 表）
- 对账白名单/黑名单（已知差异不告警）

**工作量**：2 天（与 P0-3 并行）

## 🟢 P2 — 长期演化（不影响当前）

### P2-1：子商户号 sub_mch_id

**问题**：当前只配单 `WECHAT_MCH_ID`，多家机构共用一套时需每家一个子商户号。

**应用场景**：
- 问渠 SaaS 多机构部署（每家加盟校独立商户号）
- 资金直接到各机构账户，平台不过手

**改造方案**：`WECHAT_MCH_ID` 改为按 `tenant_id` 路由（配置表 `dw_wallet_tenant_payment_config`）。

**代价**：SDK 客户端按 tenant 懒加载、证书按 tenant 部署。

**工作量**：3-5 天

---

### P2-2：异步队列

**问题**：微信回调 5 秒超时。当前同步处理：
- `handle_wechat_notify` 内做：查单+原子更新+credit_balance+流水
- 单事务跨多表
- 网络抖动/DB 慢 → 超时 → 微信重试

**改造方案**：
```
微信回调 → 落 raw_callback 表（毫秒）→ 返回 SUCCESS
            ↓
        后台 worker → 异步处理 → 写订单/流水
```

**代价**：新增 `dw_wallet_raw_callbacks` 表 + Celery worker（问渠已有 Celery 经验）。

**工作量**：3-5 天

---

### P2-3：审计日志

**问题**：当前仅业务流水（`ChargeRecord` / `RoyaltyRecord`），无审计维度（谁/何时/为什么改了账户余额）。

**改造方案**：新增 `dw_wallet_audit_logs` 表：
- 操作人（系统/管理员）
- 操作类型（手动加余额/扣减/调账）
- 操作前后余额
- 原因备注

**工作量**：2 天

## 关键判断

1. **ddw_wallet 骨架完整，但模型层需要大幅扩展**——P0 五项里有 4 项是 schema/服务层改造
2. **SDK 层完美复用**——`wechatpayv3` 集成、`alipay_client.py`、环境变量驱动的配置都是最佳实践
3. **不存在"小改即用"路径**——最小改造至少 1 周（仅 P0-1+P0-2），如果接受"问渠继续自管收款 + ddw_wallet 平行运行"，可节省改造但失去"支付中台"价值
4. **改造成本可控**——所有缺口都是已知技术栈内的工作，没有架构性难题
