## 关键判断

**直接复用部分（7 项 ✅）**：收单 + 回调 + 扣费幂等 + 入账幂等 + 分成 + 流水查询。**这意味着问渠收款链路的核心支付基础设施 100% 可复用**——不需要重写 SDK、不需要重写回调入账逻辑、不需要重写幂等。

**需要改造的部分（1 项 🟡）**：退款只写了本地记录，**真实退款链路 TODO**。需补 `_call_provider_refund`（调微信 v3 refund API）。

**需要新建的部分（5 项 🔴）**：

1. **三钱包模型** — 改 `WalletAccount` schema：增加 `recharge_balance_cents` / `income_balance_cents` / `skin_balance` 三字段，或拆为子表
2. **余额冻结** — 实现 `freeze_balance` / `unfreeze_balance`（使用预留的 `frozen_cents`）
3. **混合扣费** — `charge_with_fallback` 按优先级扣两/三个子钱包
4. **多租户** — `WalletBase` 引入 `TenantMixin`；每张表加 `tenant_id`
5. **平台抽佣** — `royalty` 逻辑扩展：扣费时先抽平台服务费，再分成作者
6. **对账引擎**（缺失但未在 13 项里）— 拉微信账单 vs 本地 PayTransaction

## 复用建议（接入问渠的最小工作）

### 立即可用（不动）
- ✅ `services/wechat_pay.py`（SDK 封装，公钥模式）
- ✅ `services/recharge.py::handle_wechat_notify`（回调入账幂等）
- ✅ `services/charge.py::charge`（按量扣费 + 幂等）
- ✅ `services/royalty.py::settle_royalty`（课件分成入账）
- ✅ `router.py::list_transactions`（流水聚合查询）
- ✅ `account.py::credit_balance / debit_balance`（乐观锁余额变更）
- ✅ `models.py::RechargeOrder / ChargeRecord`（核心表结构）

### 立即改造（1-2 天）
- 🟡 补 `_call_provider_refund` 真实退款链路
- 🔴 三钱包拆账（加 `account_type` 字段 + `get_or_create_account` 支持指定钱包类型）

### 中期规划（1-2 周）
- 🔴 多租户（加 `tenant_id` 到所有表 + 索引）
- 🔴 平台抽佣（扣费后自动按规则拆账到平台账户）
- 🔴 余额冻结/解冻（预扣费场景）

### 长期规划（1 个月+）
- 🔴 对账引擎（拉微信账单 vs 本地 PayTransaction）
- 🔴 子商户号 sub_mch_id 多机构共用

## 一句话总结

> **ddw_wallet 是"单租户 + 单钱包"的支付中台骨架**，与问渠要求的"多租户 + 三钱包 + 平台抽佣"差距明显。直接复用能拿到 ~55% 的能力（7/13），剩下 5 项缺口都是**模型层**（不是 SDK 层）改造，工作量集中在 schema 设计和账户模型抽象上。
